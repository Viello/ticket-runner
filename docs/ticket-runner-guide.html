How the Ticket Runner drives a queue of AI coding agents — end to end.

A single-page walkthrough of the real orchestration loop: a sequential queue of 4 tickets, two equal CLI agent adapters (opencode run and agy -p), the Gatekeeper's independent verification gate, retry with bounded failure triage, Context Handoffs at the token ceiling, and human-in-the-loop escalation when everything that can go wrong, does. 01 What Ticket Runner is

Ticket Runner is an external Python process — it never lives inside your codebase. You point it at a Target Project with --project-dir; it scans docs/tickets/<spec-slug>/, picks pending tickets in order, and supervises an AI coding agent subprocess that implements each one inside the Target's git working tree. The Runner alone decides when the work is done: the Gatekeeper runs the project's own test/build commands, and only a green gate — never the agent's self-report — moves a ticket to completed.

The Runner
Orchestrator process

Drives the queue, supervises worker sessions, runs the Gatekeeper, interacts via Rich TUI (nearby) or a Discord bot (away). Clean Architecture: domain ← ports ← application ← adapters.

The Worker
Agent subprocess

OpenCode or Antigravity CLI invoked headlessly per ticket. It edits the Target Project, but never commits, never edits the queue files, never pushes — and its self-reports carry no status authority.

Worker Session
ses_… / conversation_id

One OpenCode ses_… session (or Antigravity conversation_id UUID) bound to one ticket, spanning one or more Session Runs across Context Handoffs. Sessions are resumed — not rebuilt.

Gatekeeper
Independent verifier

Runs build_cmd then test_cmd from the Target's ticket-runner.yaml and enforces the dispatch baseline: only checkbox ticks may change in the ticket file between dispatch and signal.

Signal
Durable file IPC

Worker → Runner messages are strict JSON files: .agent/signals/{ticket_id}_ready.json and .agent/questions/{ticket_id}.json. Model stdout is never parsed for state.

Context Handoff
Token-budget compaction

At 135k tokens the supervisor ends the Session Run, asks the Worker to write a 5-section checkpoint to .agent/checkpoints/{ticket_id}/handoff.md, then resumes with a fresh session reading it.

Circuit Breaker
Escalation halt

3 failed Verification Attempts (worker run + signal validation + gate) trip the breaker: state becomes CIRCUIT_BREAKER_TRIPPED, the queue halts, and a human must untangle it.

Evidence Card
Human sign-off artifact

In human mode, green checks pause before commit and present an Evidence Card (test status, harness status, bounded evidence paths, unticked criteria) via terminal prompt or Discord /approve.

Fidelity note. Every identifier in this guide is real: command flags (--variant vs --effort, --session ses_… vs --conversation uuid), state file schemas (runner/domain/state.py, runner/domain/signal.py), module names (QueueOrchestrator, WorkerSupervisor, EvidenceTriage), and the ticket document format (Specimen A bold-label headers — **Mode:**, **Status:**, **Blocked by:** — with - [ ] acceptance criteria). Ticket IDs follow the enforced pattern ^T\d{3,}$ — T001, not T-001. Timestamps and hashes are simulated.

The Runner is wired at the Composition Root (runner/container.py): adapters are chosen once per session — worker.provider: "opencode" | "antigravity" selects the AgentWorker implementation — then every subsystem talks to ports, never to concrete CLIs. Adapter switching in current builds. worker.provider is bound per session by the overlay config — the worker factory is decided once in runner/container.py. A queue that names a different agent between tickets (as our scenario does) is served by restarting the Runner with the matching provider: the queue is idle between tickets, Doctor re-validates the new CLI, and selected_model/state simply persists. Both adapters implement the identical AgentWorker protocol, so workflow shape, signals, and gates never change — only the normalized flags do (--variant ↔ --effort, --session ses_… ↔ --conversation uuid).

## Operational Guardrails & Completion Protocol
## Invariants (extracted from AGENTS.md, sanitized):
- opencode invoked as a subprocess, never a daemon; resume with the same session id
- Worker implements via worker.execution_skill — it may tick Acceptance criteria, nothing else
- Worker↔Runner state is durable JSON files — never parse model stdout
- Only the Gatekeeper passes a ticket (build/test commands); 3 failed attempts trip the Circuit Breaker
- All automated work on agent/ticket-runner; never git push (pre-push hook blocks it)
- Commit format: <type>(<scope>): Title with layer scoping, no ticket numbers, no trailing periods
- Token budget: warn 120k / handoff 135k / ceiling 150k (checkpoint via .agents/skills/handoff/SKILL.md)
- One commit per ticket by the Gatekeeper; .agent/ is untracked

1. No Git staging, commits, or queue mutations — Worker may tick - [ ] → - [x] under the
   Acceptance criteria of the active ticket file; every other edit under docs/tickets/ is forbidden.
2. Review self-checks — 3-axis code review (Standards/Spec/Security) recorded in self_review_notes;
   this ticket is Security: required → also read .agents/skills/security-review/SKILL.md.
3. Debugging guidance — non-trivial failures: read .agents/skills/diagnosing-bugs/SKILL.md.
4. Ready signal protocol — when done, write .agent/signals/T001_ready.json with the exact schema
   (ticket_id / status ready_for_verification / modified_files / self_review_notes / new_gotchas / timestamp / scope).
5. Question protocol — blocked or ambiguous → .agent/questions/T003-style file and STOP; never guess.

Gatekeeper ground rules

  • Dispatch baseline: the ticket file snapshot taken before dispatch decides what changed. Any edit except - [ ] → - [x] under ## Acceptance criteria restores the baseline and rejects the signal — burning an attempt. (Security boundary against prompt-injected ticket rewrites.)
  • Token-preserving triage: full gate logs stay in .agent/evidence/…/harness.log; the retry prompt gets ≤ 30 lines / 1,000 characters via .agent/evidence/…/summary.json.
  • Commit discipline: exactly one commit per ticket — code, tests, runner-appended gotchas.md, and the relocated ticket whose header records **Status:** completed and a **Completed:** timestamp. The commit SHA lives in git, never in the ticket.
  • Branch + push posture: everything happens on agent/ticket-runner; .git/hooks/pre-push blocks remote pushes outright (ADR 0005). The Runner commits; the Worker never does.
  • HITL gates: a ticket with **Mode:** HITL pauses before dispatch; green checks in approval_mode human pause before commit with an Evidence Card (/approve, /reject, /diagnose).
