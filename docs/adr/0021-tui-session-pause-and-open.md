# TUI Session: Pause-and-Open Interactive Access via [o] Hotkey

When the user needs to inspect or directly interact with an active Worker Session from their own terminal, the Runner must hand off control safely without running two concurrent processes against the same OpenCode session. We chose a pause-and-open protocol: the Runner waits for the next signal boundary (never mid-Session-Run), presents a two-key confirmation (`[o]` → `[y]`/`[n]`), freezes the Rich dashboard, then spawns a new terminal process running `opencode --session <id>` in interactive TUI mode using the host configured under `ui.session_terminal` in `config.yaml`. The terminal host is detected once by the Doctor (priority: wt.exe → pwsh.exe → powershell.exe → cmd.exe), user-selected, and written to `config.yaml` — not re-detected on every startup. State schema gains `tui_open: bool` and `tui_session_id: string|null` so crash recovery can warn that the Runner exited while TUI was open. On window close the Runner injects a short resume banner via `--auto` before starting a fresh Session Run. The alternative — attaching a second concurrent process to the live session — was rejected because it creates a race on OpenCode's on-disk session state, hides all TUI-consumed tokens from the 135k handoff budget, and bypasses the Gatekeeper and Signal protocol entirely.
