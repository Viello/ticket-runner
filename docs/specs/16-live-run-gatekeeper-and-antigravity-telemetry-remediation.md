# Spec 16: Live-Run Gatekeeper Shell Quoting, Antigravity Telemetry Parity, and Autonomous Ticket Boundary Remediation

## Problem Statement

During the live Human-in-the-Loop execution of the `orchestrate-runner` sequence against the `agent-skills` Target Project (`T101` → `T102` under the `antigravity` Worker provider), the Worker successfully authored all eight missing Codex interface metadata files (`*/agents/openai.yaml`), but the Queue halted before reaching the Human-in-the-Loop Evidence Card due to three interacting architectural defects in the Runner and its provisioned Worker Skill:

1. **Windows Gatekeeper Shell Quote Corruption**: The Gatekeeper wraps `verification.test_cmd` and `verification.build_cmd` into platform shell argv tokens (`cmd.exe /d /s /c <command>` on Windows per ADR 0016) and spawns them via `asyncio.create_subprocess_exec`. On Windows, Python's `subprocess.list2cmdline` serializer wraps the command argument in outer double quotes and backslash-escapes every internal double quote (`"` → `\"`). Because `cmd.exe` does not recognize `\"` as an escape sequence, any verification command containing double-quoted strings (such as `python -c "import glob,yaml; ..."`) is passed to the child binary with literal `\"` tokens. Python's C runtime splits the argument at the first internal space (`"import`), crashing with `SyntaxError: unterminated string literal` on every Verification Attempt and causing the Failure Analyser to emit a false `FLAKY` escalation.
2. **Inert Token Telemetry, Cumulative `result.usage` Distortion, and End-of-Turn Handoff Race Under Antigravity**:
   - While `AntigravityWorker` decodes NDJSON streaming envelopes (`init`, `step_update`, `result`) and attaches `TokenUsage`, `WorkerSupervisor` only processes step progress and token usage when the event type equals OpenCode's `"step_finish"`, and only forwards tool activity to `TerminalDisplay` on `"tool_call"` or `"tool_use"`. Consequently, `.agent/state.json` (`tokens.current`), `.agent/status.json` (`token_count`), and diagnostic reports remain stuck at `0 / 150,000`.
   - Furthermore, empirical inspection of `T101` session logs reveals three subtle traps when wiring Antigravity events into `WorkerSupervisor` and `HandoffCoordinator`:
     - **Stall / Heartbeat Timer Trap**: In `AntigravityWorker`, tool-invocation `step_update` events (`step_type == "tool"`) and streaming deltas have `token_usage is None`. If `last_step_time` only updates when `token_usage is not None`, long chains of tool calls without intermediate usage payloads fail to advance `last_step_time`.
     - **End-of-Turn Ready Signal vs. Handoff/Ceiling Race**: In `HandoffCoordinator.run_cycle`, `KILLED_CEILING` (Step 2) and `KILLED_HANDOFF` (Step 4) are evaluated *before* checking whether `.agent/signals/<ticket_id>_ready.json` is already on disk (Step 5), and `WorkerSupervisor` triggers `_on_budget_action` kills even after `_signal_first_seen_at` is set. If a Worker crosses 135k or 150k on the final step where it writes `<ticket_id>_ready.json` (or on the closing `result` envelope), the Runner discards the finished Ticket and launches a redundant Context Handoff or ceiling escalation.
     - **Cumulative `result.usage` vs. Context Occupancy (ADR 0015)**: In `agy`, `step_update.usage.total_tokens` equals `input_tokens + output_tokens` (omitting `cache_read_tokens`), so true context-window occupancy at step $N$ is `input_tokens + cache_read_tokens + output_tokens + thinking_tokens` (~39.7k tokens at step 71 of `T101`), whereas `result.usage` at the end of the turn is the *cumulative sum* across all 36 steps (`total_tokens: 174,681`, `cache_read_tokens: 788,393`). Feeding `result.usage` directly into `BudgetMonitor.observe()` violates ADR 0015 and falsely trips the 150k ceiling on a 40k-context turn.
3. **Ambiguous Autonomous Ticket Ownership in the Implementation Worker Skill**: The `implement` Worker Skill marks Step 5 (`Commit`) as interactive-only (`skip in Ticket Runner autonomous execution`), but leaves Step 4 (`Ticket Transition & Gotchas`: append to `docs/tickets/gotchas.md`, stamp `Status: completed`, and relocate the Ticket file to `completed/`) and Step 6's readiness criteria unconditional. Furthermore, `PromptBuilder` forbids `git add` and `git commit` without forbidding mutations under `docs/tickets/`. When a Worker obeys Step 4 during autonomous execution, it moves the active Ticket into `completed/` before emitting `.agent/signals/<ticket_id>_ready.json`. This corrupts the Queue lifecycle in two ways: (a) if Gatekeeper verification passes and the operator approves the Evidence Card, `DirectoryTicketStore.finalize_completed` raises `TicketFormatError: Ticket file not found` because the source Ticket path is already gone; and (b) if the Runner restarts, `CrashRecovery` sees the Ticket inside `completed/` with `Status: completed`, resets `.agent/state.json` to `IDLE`, and silently skips Gatekeeper verification and commit for that Ticket.

## Solution

Close all three live-run defects at their existing architectural seams so the Runner can drive `T101` → `T102` (and any future Target Project Queue) end-to-end on Windows under the `antigravity` provider:

1. **Preserve Quoting in Windows Shell Verification Commands**: Update the Gatekeeper / `CommandRunner` shell execution seam on Windows so `cmd.exe /d /s /c` commands execute without `list2cmdline` backslash-escaping corrupting embedded double quotes, while preserving Windows Job Object process-tree reaping, concurrent stdout/stderr streaming, and timeout/silence enforcement (ADR 0016).
2. **Unify WorkerSupervisor Telemetry Across Agent Backends**: Extend `WorkerSupervisor` event processing so `TokenUsage` carried on Antigravity `step_update` and `result` events is observed by `BudgetMonitor`, persisted to `.agent/state.json` (`tokens.current`, `warning_sent`), published to `.agent/status.json` (`token_count`, `STEP_FINISHED`), and reflected in `TerminalDisplay` alongside Antigravity tool-invocation `step_update` events.
3. **Enforce Strict Gatekeeper Ownership of `docs/tickets/`**: Update the `implement` Worker Skill (in both the Runner repository and provisioned Target Project copies) and `PromptBuilder` operational guardrails so ticket frontmatter updates (`Status: completed`), `completed/` relocation, and `docs/tickets/gotchas.md` appends are strictly forbidden in autonomous Runner mode (where the Worker passes `new_gotchas` via `.agent/signals/<ticket_id>_ready.json` with `status: "ready_for_verification"`). Add idempotent fallback handling in `DirectoryTicketStore.finalize_completed` so a pre-relocated Ticket file never crashes post-approval commit finalization.
4. **Sanitize Target Project State for Clean Resumption**: Reset the uncommitted dirty state in the Target Project (`D:\Repos\agent-skills`) left by the halted `T101` run so `T101` and `T102` execute cleanly from baseline commit `6912328` under live Overseer telemetry polling.

## User Stories

1. As an operator running Ticket Runner on Windows, I want Gatekeeper `verification.test_cmd` and `verification.build_cmd` strings containing double-quoted arguments (such as `python -c "import glob,yaml; ..."`) to execute without `\"` quote corruption, so that valid one-liner verification commands pass with exit code 0 instead of crashing with `SyntaxError`.
2. As an operator, I want Windows Gatekeeper shell commands to continue running inside a Windows Job Object with process-tree termination on timeout or silence-window expiry, so that fixing quote escaping does not regress hung-process cleanup (ADR 0016).
3. As an operator using the `antigravity` Worker provider, I want `.agent/state.json` (`tokens.current`) and `.agent/status.json` (`token_count`) to update in real time with true per-step context-window occupancy (including `cache_read_tokens` per ADR 0015) as `step_update` events arrive, without being inflated by `result.usage`'s multi-step cumulative sum.
4. As an operator using the `antigravity` Worker provider, I want `last_step_time` to update on every completed step and tool invocation regardless of whether `token_usage` is present on that event, so that long sequences of tool calls do not falsely trigger idle heartbeats or stall timeouts.
5. As an operator using any Worker provider, I want a valid `.agent/signals/<ticket_id>_ready.json` on disk to take precedence over a late 135k Context Handoff (`KILLED_HANDOFF`) or 150k hard ceiling (`KILLED_CEILING`) threshold crossed on the final turn step or closing `result` envelope, so that the Runner never throws away a completed Ticket to run a redundant handoff session.
6. As an operator using the `antigravity` Worker provider, I want `BudgetMonitor` to evaluate context occupancy during active steps when no ready Signal is present, so that genuine mid-ticket context growth triggers the 120k warning, 135k Context Handoff, and 150k hard ceiling thresholds reliably (ADR 0015).
7. As an operator watching the `TerminalDisplay` during an Antigravity Session Run, I want active tool invocations (`step_update` events with `step_type == "tool"`) and assistant step summaries to stream into the UI event sink, so that the live terminal dashboard shows Worker progress just as it does for OpenCode.
8. As a Gatekeeper generating a diagnostic report (`.agent/logs/<ticket_id>_diagnostic.md`) after an Antigravity failure, I want `Token budget: <current> / <ceiling>` to display the actual context tokens occupied in that Session Run rather than `0 / 150,000`.
9. As a Worker agent reading `.agents/skills/implement/SKILL.md` in autonomous Ticket Runner mode, I want Step 4 (`Ticket Transition & Gotchas`) and Step 6 explicitly scoped so that I never edit `docs/tickets/gotchas.md`, never stamp `Status: completed`, and never move the Ticket file to `completed/` myself.
10. As a Worker agent reading `.agents/skills/implement/SKILL.md` in autonomous Ticket Runner mode, I want Step 6 to state the complete ready Signal requirement (`status: "ready_for_verification"`, `modified_files`, `self_review_notes`, `new_gotchas`, `timestamp`) or defer explicitly to the prompt's `<communication_protocol>`, so that I never emit an incomplete or schema-invalid `.agent/signals/<ticket_id>_ready.json`.
11. As a Worker agent receiving a prompt from `PromptBuilder`, I want the Operational Guardrails section to explicitly forbid modifying, moving, or deleting any file under `docs/tickets/` (including the active Ticket markdown file and `docs/tickets/gotchas.md`), so that queue state mutations remain exclusively with the Gatekeeper (ADR 0002, ADR 0012).
12. As a Gatekeeper finalizing an approved Ticket via `DirectoryTicketStore.finalize_completed`, I want idempotent handling if the Worker already moved the Ticket file into `completed/` during the session, so that human `[y]` approval on the Evidence Card still updates `Status: completed` / `Completed: <timestamp>` and authors the atomic commit instead of crashing with `TicketFormatError: Ticket file not found`.
13. As an operator resuming after an aborted or failed run where a Worker prematurely moved a Ticket to `completed/` without a Gatekeeper commit, I want pre-run sanitization guidance and clean working-tree restoration so that `CrashRecovery` does not mistake an uncommitted file move for a completed Ticket.
14. As a Live Runtime Overseer monitoring `.agent/` during `T101` → `T102`, I want Gatekeeper verification to pass with `validated 45 openai.yaml files`, pause `TerminalDisplay` cleanly at the Human-in-the-Loop Evidence Card, author one atomic conventional commit per Ticket upon `[y]` approval, and complete the Queue with `0` anomalies.

## Implementation Decisions

- **Windows Shell Command Execution Seam (`GatekeeperCommandExecutor` / `SubprocessRunner`)**:
  - Keep ADR 0016 intact: Gatekeeper verification commands remain operator-authored shell strings executed through `cmd.exe /d /s /c` on Windows and `/bin/sh -c` on POSIX.
  - Eliminate the `subprocess.list2cmdline` double-quote corruption when spawning `cmd.exe /d /s /c <command>` on Windows. When `create_subprocess_exec` is called with `cmd.exe`, Python passes the argv list through `list2cmdline`, which turns `"..."` into `\"...\"` — syntax that `cmd.exe` does not unescape. Instead, on Windows when spawning a shell command (or when `cmd[0]` resolves to `cmd.exe` with `/c`), invoke `asyncio.create_subprocess_shell` with the raw command string (or pass the unescaped command tail to `cmd.exe /d /s /c "<command>"` via `create_subprocess_shell`), while retaining the `WindowsJobObject` assignment, `DEFAULT_STREAM_LIMIT`, and concurrent stderr draining in `SubprocessProcessHandle`.
  - Verify that commands containing nested double quotes, single quotes, semicolons, and spaces (specifically `python -c "import glob,yaml; fs=glob.glob('*/agents/openai.yaml'); [yaml.safe_load(open(f,encoding='utf-8')) for f in fs]; print('validated %d openai.yaml files' % len(fs))"`) execute identically on Windows to running them directly in a console.
- **Provider-Agnostic Token & Step Telemetry in `WorkerSupervisor`, `AntigravityWorker`, and `HandoffCoordinator`**:
  - **Separate `last_step_time` / `step_counter` from `token_usage` Presence**:
    - In `WorkerSupervisor`, update `last_step_time = self._clock()` and increment `step_counter` on every completed step event (`event.type == "step_finish"` for OpenCode, or `event.type == "step_update"` with `part.get("state") in ("DONE", "ERROR")` for Antigravity) and update `last_step_time` on active tool invocations (`step_type == "tool"`), **independently** of whether `event.token_usage` is `None`. This guarantees that long sequences of tool calls (which carry `token_usage is None` in Antigravity) never starve `last_step_time`.
  - **Per-Step Context Occupancy vs. Cumulative `result.usage` in `AntigravityWorker` (ADR 0015)**:
    - In `agy`, `step_update.usage.total_tokens` equals `input_tokens + output_tokens` (excluding `cache_read_tokens` and `thinking_tokens`), whereas true context-window occupancy for that step is `input + output + reasoning + cache_read + cache_write` (because `TokenUsage.occupancy` returns `self.total` whenever `total is not None`, setting `total=total_tokens` on `step_update` under-reports cached context occupancy by ~35k tokens). Conversely, `result.usage` at the end of a multi-step `agy` turn is the **cumulative sum** of all `step_update.usage` dictionaries across the entire turn (e.g., 174,681 `total_tokens` and 788,393 `cache_read_tokens` summed across 36 steps on a turn whose peak context window was ~39.7k tokens).
    - To honor ADR 0015 (which compares budget thresholds against current context-window occupancy rather than cumulative multi-step spend):
      - For Antigravity `step_update` events carrying `usage`, compute `TokenUsage` with `total=None` (or `total = input + output + reasoning + cache_read + cache_write`) so `TokenUsage.occupancy` reflects the full context window (`input_tokens + cache_read_tokens + output_tokens + thinking_tokens`) at that step.
      - For Antigravity `result` events, do **not** feed `result.usage` into `BudgetMonitor.observe()` when `step_update` usage has already been observed during the turn (using `result.usage` only if no `step_update` usage was emitted, such as a single-shot response, while still using `result.usage` inside `_detect_empty_success_result` anomaly detection).
  - **Ready Signal Precedence Over `KILLED_HANDOFF` / `KILLED_CEILING`**:
    - In `WorkerSupervisor`: before triggering `KILLED_HANDOFF` or `KILLED_CEILING` via `_on_budget_action` (or when evaluating budget actions on the final step/result), check `self._signal_first_seen_at is not None or self._is_signal_present(ticket_id)`. If the Worker has already emitted `.agent/signals/<ticket_id>_ready.json`, suppress `KILLED_HANDOFF` / `KILLED_CEILING` so the process exits cleanly (or terminates via `KILLED_SIGNAL` after the grace window) with the ready Signal intact.
    - In `HandoffCoordinator.run_cycle`: check whether a valid ready Signal is present on disk (`read_ready(ticket.id) is not None`) **before** branching into the `KILLED_CEILING` (Step 2) or `KILLED_HANDOFF` (Step 4) escalation/handoff flows. A valid ready Signal on disk always wins over a late budget threshold crossing.
  - **UI Tool-Event & Step Status Forwarding**:
    - Whenever a step with `event.token_usage is not None` is observed (and not skipped as a cumulative `result` sum), record occupancy via `StateCoordinator.record_tokens()` and publish `StatusEvent(last_event="STEP_FINISHED", token_count=latest_occupancy)` to `StatusPublisher`.
    - Extend UI tool-event forwarding in `WorkerSupervisor` so Antigravity tool steps (`event.type == "step_update"` where `event.part` has `step_type == "tool"` and `state == "ACTIVE"`) format the tool name and parameters and emit to `_ui_event_sink` alongside `"tool_call"` / `"tool_use"`.
- **Autonomous Queue & Gotchas Boundary (`implement` Worker Skill, `PromptBuilder`, `DirectoryTicketStore`)**:
  - Update `.agents/skills/implement/SKILL.md` (and synchronize the provisioned copy in the Target Project):
    - Annotate Step 4 (`Ticket Transition & Gotchas`) with `*(interactive mode only — skip in Ticket Runner autonomous execution; pass new gotchas via the ready signal JSON and let Gatekeeper relocate the ticket)*`.
    - Update Step 6 (`Readiness & Live QA`) so autonomous readiness requires passing targeted and broad tests, completing `/code-review` (and `/security-review` when flagged), and emitting `.agent/signals/<ticket_id>_ready.json` with `"status": "ready_for_verification"` and all required schema fields — explicitly stating that ticket relocation and `docs/tickets/gotchas.md` updates are performed by the Gatekeeper after verification and human approval.
  - Update `PromptBuilder` operational guardrails:
    - Expand Guardrail 1 (`No Git Staging, Commits, or Queue File Mutations`) to explicitly forbid running `git add` / `git commit`, editing `docs/tickets/gotchas.md` directly, or modifying/moving/deleting any Ticket markdown file under `docs/tickets/`.
  - Harden `DirectoryTicketStore._resolve_source_path` / `finalize_completed`:
    - If `ticket.path` does not exist at its original pending location because the Worker prematurely moved it to `<queue_dir>/completed/<ticket_filename>.md`, locate the file inside `completed/`, rewrite its frontmatter (`Status: completed`, `Completed: <ISO-8601-UTC-timestamp>`) in place, and return cleanly instead of raising `TicketFormatError`.
- **Target Project Pre-Run Sanitization (`D:\Repos\agent-skills`)**:
  - Before re-running `ticket-runner start --local-only` on `D:\Repos\agent-skills`, restore `docs/tickets/01-runner-live-test-bootstrap/T101-add-codex-interface-metadata-to-skills-lacking-it.md` and `docs/tickets/gotchas.md` (`git checkout -- docs/tickets/`), remove the untracked `docs/tickets/01-runner-live-test-bootstrap/completed/` directory, and remove stale `.agent/state.json`, `.agent/status.json`, `.agent/logs/T101_diagnostic.md`, and `docs/tickets/.queue.lock`.

## Testing Decisions

- **What makes a good test**: Tests must assert observable external behavior at existing application and adapter seams (exit codes, stdout/stderr tails, `.agent/state.json` and `.agent/status.json` payloads, budget termination reasons, and git/filesystem state) rather than internal private helper calls.
- **Seam 1 — `GatekeeperCommandExecutor` + `SubprocessRunner` (Windows Shell Quoting Integration)**:
  - Drive `GatekeeperCommandExecutor.verify` with a real `SubprocessRunner` on Windows using a `VerificationConfig` whose `test_cmd` is the exact double-quoted Python YAML-validation one-liner (`python -c "import glob,yaml; ..."`). Assert `report.passed is True`, `exit_code == 0`, and stdout contains `validated`.
  - Prior art: existing Gatekeeper command execution tests in `tests/unit/application/test_gatekeeper.py` and `SubprocessRunner` tests in `tests/unit/adapters/test_subprocess_runner.py`.
- **Seam 2 — `WorkerSupervisor`, `AntigravityWorker`, & `HandoffCoordinator` (Token Occupancy, Stall Timer Separation, and Ready-Signal Precedence)**:
  - Drive `WorkerSupervisor.run` with `AntigravityWorker` and a fake `CommandRunner` streaming realistic `init`, `step_update` (both `step_type: "tool"` with `usage: None` and `step_type: "agent_response"` with `input_tokens` + `cache_read_tokens`), and `result` (with cumulative multi-step `usage`) JSONL lines.
  - Assert that:
    1. `last_step_time` and `step_counter` advance on completed tool `step_update` events even when `token_usage is None`.
    2. `StateCoordinator` and `StatusPublisher` record true per-step context occupancy (`input + cache_read + output + reasoning`, e.g., ~39.7k) rather than `step_update.usage.total_tokens` (3.9k) or `result.usage`'s cumulative multi-step sum (174.6k).
    3. When a genuine mid-turn `step_update` crosses 120k / 135k / 150k without a ready Signal on disk, `BudgetMonitor` triggers `WARN`, `KILLED_HANDOFF`, and `KILLED_CEILING` respectively.
    4. When `.agent/signals/<ticket_id>_ready.json` is already present on disk when 135k (`KILLED_HANDOFF`) or 150k (`KILLED_CEILING`) is crossed, both `WorkerSupervisor` and `HandoffCoordinator.run_cycle` preserve the ready outcome (`SingleCycleStatus.READY`) instead of discarding the finished Ticket into a handoff or ceiling escalation.
  - Prior art: `tests/unit/application/test_worker_supervisor.py`, `tests/unit/application/test_handoff_coordinator.py`, and `tests/unit/adapters/test_antigravity_worker_adapter.py`.
- **Seam 3 — `PromptBuilder` & `DirectoryTicketStore.finalize_completed` (Queue Ownership Boundary)**:
  - Assert `PromptBuilder.build_prompt` includes the explicit prohibition against moving Ticket files to `completed/` or editing `docs/tickets/gotchas.md` directly.
  - Assert `DirectoryTicketStore.finalize_completed` succeeds idempotently when a Ticket file has already been moved into `completed/` prior to finalization, updating `Status: completed` and `Completed:` without raising `TicketFormatError`.
  - Prior art: `tests/unit/application/test_prompt_builder.py` and `tests/unit/adapters/test_ticket_store.py`.

## Out of Scope

- Adding new CLI flags or changing the `ticket-runner.yaml` configuration schema.
- Modifying the `AgentWorker` port interface or changing OpenCode's event decoding contract.
- Changing the 3-attempt Circuit Breaker threshold or token budget limits (120k / 135k / 150k).
- Automating the Human-in-the-Loop Evidence Card sign-off or replacing the post-run `/live-qa` ritual.
